# Portfolio Page Design

## Intent and why

Aaron currently has no single place to see the health of his whole customer
book at a glance. The existing viewer is account-at-a-time (Customer Updates
cards, the Day Plan page) or task-at-a-time (Asana Overdue/Due lists). There
is no daily "which of my accounts need attention right now" view.

This feature adds **Portfolio**: a new page, scoped to Aaron's own accounts,
that he opens daily to (a) check overall account health across his book and
(b) decide which account(s) to focus on today. It is a triage tool, not a
QBR deck — density and honesty about data quality matter more than polish.

**Naming note:** this is *not* the existing "My Customers" toggle on the
Environments tab (`viewer/webapp/templates/environments.html`), which
filters the org-wide environments/customer list down to Aaron's accounts by
fuzzy name match. That feature is unrelated (infrastructure/environments
data) and keeps its name. This new page is called **Portfolio** specifically
to avoid colliding with it.

## Goals

- One page, opened daily, showing every account in Aaron's book (primary +
  secondary from `account-config.json`) grouped by health.
- Surface ARR, renewal date, health score, and CSM/AE/TAM owners per
  account, sourced from that account's existing Account Context Doc (the
  Google Doc produced by the separate `account-context` skill).
- A synthesized "This week" callout: the sharpest cross-account findings,
  generated by `daily-brief-generation` (not hand-written, not computed by
  this webapp).
- Make data quality visible, not hidden: every figure shows how stale it is
  (days since last swept) and whether it's internally disputed across
  sources. Missing data reads as an explicit placeholder, never a silently
  blank field.
- A concrete "next step" per account, and a real, always-available
  `claude://` deep link to refresh that account's Context Doc on demand.
- A triage panel (opened from a stat tile) that lists just the matching
  accounts' next steps, for a fast daily pass without reading every card.

## Non-goals

- No live Salesforce/Gainsight API integration. Every commercial/health
  figure continues to flow through Glean-indexed research the way
  `account-context` already produces it.
- No changes to the `account-context` skill (`camunda/actora`) in this
  round. A structured JSON sidecar next to its Doc output would make
  parsing far more reliable, but that's deliberately deferred — this round
  ships with best-effort parsing of the existing prose/table Doc content.
- No changes to the Environments tab's "My Customers" toggle.
- Not a replacement for Customer Updates or Day Plan — those stay as they
  are; Portfolio is a new, additional view.

## Anti-goals

(What would make this a failure even if it technically works.)

- Showing a confident-looking number that's actually one of several
  disputed values, with no indication of the disagreement. Several of
  Aaron's real accounts have exactly this problem today (e.g. Goldman
  Sachs has 5 conflicting ARR figures across sources) — presenting one of
  them as *the* number is worse than not showing it.
- Silently dropping an account because its Context Doc is missing or
  unparseable. Every account in `account-config.json` must appear on the
  page, even if every field reads "No research yet."
- A page that's expensive enough (per-account live Glean searches on every
  load) that Aaron stops opening it daily.

## Constraints

- Must read the real account list from `/config/account-config.json`
  (primary + secondary), the same source every other account-aware part of
  this app already uses.
- Must reuse this app's existing visual language (the CSS custom-property
  theme in `day_plan.html`/`brief_fragment.html` — `--bg`, `--surface`,
  `--t1`/`--t2`/`--t3`, `--accent`, `--good`/`--bad`, `--r`, etc.), so the
  page looks native to the rest of the viewer, not a bolt-on.
- Must work with the webapp's existing Google OAuth scope
  (`https://www.googleapis.com/auth/drive`, already granted per-user — see
  `app.py`). This scope is broad enough to read a shared-drive Context Doc
  the signed-in user has access to; Drive API calls into it must pass
  `supportsAllDrives=True` / `includeItemsFromAllDrives=True`, matching the
  pattern already used in `gdrive_briefs.py` (e.g. line 826).
- Must not assume `account-config.json`'s `gdrive_folder_id` points at the
  Context Doc's location — that field is this app's own per-account docs
  folder, a different, possibly-unrelated location from the org-wide
  canonical Context Doc path (`Consulting Shared Drive → Customers →
  {first letter} → {account} → "{Account} Context"`, per
  `account-context`'s `invocation-contract.md`). Resolve the Context Doc by
  searching Drive for a Doc titled "{account_name} Context" (fuzzy on
  name, same folding rules `account-context` itself uses — case,
  punctuation, legal suffixes). **Don't write this resolution logic from
  scratch** — `gdrive_briefs.py` already has it, built for the Environments
  "My Customers" toggle: `CONSULTING_CUSTOMERS_FOLDER_ID`,
  `_letter_bucket`, `_find_folder_in_shared_drive`, and
  `_normalize_account_name` (lines ~640-728) do exactly this folder
  resolution and name-folding today. Reuse these rather than
  reimplementing account-name matching a second way.
- The "This week" callout is **not** generated by this webapp. It's a new
  item (`section: portfolio-summary`, `item_key: portfolio-summary-callout`)
  being added to `daily-brief-generation` (`camunda/actora`) in a parallel
  piece of work (session `local_faf47955-865f-4b40-84bf-3ccfb9dcbd2a` as of
  this writing). This page reads that item the same way it reads any other
  brief section, and must degrade gracefully (omit the callout, don't
  error) if the item doesn't exist yet or hasn't been generated for today.

  **Pinned Drive contract** (confirmed with the parallel work, not a
  guess): a new file `portfolio-summary.json` in `/briefs/{brief_date}/`,
  a bare object matching this skill's own established item shape
  (`item_type`, not `type`; no file-level `generated_at` — every other
  item file omits it too, since it's cache-internal or DB-assigned at
  ingestion):
  ```json
  {
    "item_type": "card",
    "section": "portfolio-summary",
    "item_key": "portfolio-summary-callout",
    "content": { "findings": ["One plain sentence per finding, no numbering or markdown.", "..."] }
  }
  ```
  `findings` holds 3-5 plain-text sentences; this page adds the numbered-list
  markup itself. This webapp must add a `portfolio-summary` entry to
  `gdrive_briefs.py`'s `_FILE_TO_SECTION` map (currently lines 58-64; only
  `today.json`, `meetings.json`, `action-items.json`, `fyi.json`, and
  `manager-update.json` are registered) — without it, `read_section()` will
  never see this file regardless of whether the parallel work has shipped
  it. Treat "file not found" and "found but `findings` is empty" the same
  way: hide the callout, since the anti-goals above rule out guessing at
  which case it is.
- `claude://` refresh deep links follow the pattern already established by
  the Day Plan page's own Refresh link (`day_plan.html`'s
  `dp-refresh-link`, now merged to `main` via PR #90): `account-context` is
  invoked by natural language, not a slash command, so the link must read
  `claude://claude.ai/new?q=` + URL-encoded `refresh the context for
  {Account Name}`.

**Branch sequencing (resolved):** this worktree was rebased onto `main`
after PR #90 (Day Planning) merged, so `day_plan.html`, its toolbar link,
and `test_toolbar_day_plan_link.py` are all present here now — mirror them
directly rather than reproducing the pattern from scratch.

## The design, as decided

### Page structure

1. **Header** — title "Portfolio", subtitle with signed-in email and
   account count. A back link to the main briefs list, matching the
   existing page header pattern.
2. **Stat tiles row** (4 tiles, each clickable — opens the triage panel,
   see below):
   - **Accounts** — total count. Opens panel listing all accounts.
   - **Combined ARR** — sum of parseable ARR figures, with a note of how
     many are disputed (e.g. "3 of 5 figures disputed"). Opens panel
     filtered to accounts whose ARR is flagged uncertain.
   - **Needs Attention** — count of accounts in the worst health group.
     Opens panel filtered to that group.
   - **Stale Data (>30d)** — count of accounts whose Context Doc is more
     than 30 days past its last sweep. Opens panel filtered to those.
3. **"This week" callout** — numbered list rendered from the
   `portfolio-summary-callout` item described above. Hidden entirely (not
   an empty box) if that item isn't available for today.
4. **Account cards**, grouped under health-group headers, in this fixed
   order: **Needs Attention** (red) → **Watch** (yellow) → **Healthy**
   (green) → **No Health Data** (gray, unknown last). Each group header
   shows the group's account count and ARR subtotal.

### Health grouping (derived, not stored)

Parse the Context Doc's health signal and map it to one of four groups.
Match case-insensitively on color words near "health" or "Gainsight" in
the doc text:

| Signal found | Group |
|---|---|
| "Red" | Needs Attention |
| "Yellow", "Amber", "Orange" | Watch |
| "Green", "Lime Green" | Healthy |
| No health color found anywhere in the doc | No Health Data |

When a doc mentions more than one score (e.g. "C8: Green, Overall:
Yellow" — several of Aaron's real accounts do this), group by the
**worse** of the two, and show both in the card's Health field with a
note that they disagree.

This is a distinct concept from two other "tier" ideas already in this
codebase and must not be confused with them in code or UI copy:
- `account-config.json`'s `tier` field (`primary`/`secondary`) — run
  cadence, unrelated to health.
- The Context Doc's own commercial tier/edition (e.g. "Enterprise",
  "Self-Managed") — shown in the card as a small pill, informational only.

### Account card (uniform layout — every account, every group)

Every card shows the same fields in the same order, regardless of group.
A field with no parseable value reads as an explicit placeholder ("Not
captured this sweep") — never omitted, so cards stay scannable side by
side.

Top row: account name, health badge, commercial-tier pill, "swept Nd ago"
pill (computed from the Doc's "Last swept: YYYY-MM-DD" line, falling back
to the Drive file's modified-time if that line isn't found).

Field grid (2 rows x 3 columns):
- **ARR** — parsed dollar figure. If the surrounding text contains any of
  `conflict`, `disagree`, `unreconciled`, `disputed`, `does not reconcile`,
  flag it uncertain and show the note found nearby.
- **Renewal** — parsed date, or "Not captured this sweep".
- **Health** — the color(s) found, as described above.
- **CSM**, **AE**, **TAM** — parsed from a "CSM:"/"AE:"/"TAM:" label or an
  equivalent table row (docs vary between inline labels and a `Field,
  Detail` CSV-style table — match both). "You" when the parsed name
  matches the signed-in user.

Below the grid:
- **Risks** — a short bullet list pulled from the doc's risk/issue section
  (docs vary in heading — match on "Top open risks", "Open Risks & Issues",
  or a "Blockers/Risks" style heading), each with its source tag if one is
  present in the text (e.g. "[Gainsight via Glean, ...]").
- **Next step** — one sentence. Best-effort: pull the first actionable
  recommendation sentence the doc's own "recommendation"/"next"/"decide"
  language surfaces; if none is found, fall back to a generic "Review this
  account's Context Doc for next steps" rather than inventing one.
- **Footer**, two links, always both present and always active (no
  disabled states):
  - "Open Context doc →" — the Doc's own URL.
  - "Refresh research" — `claude://claude.ai/new?q=` + URL-encoded
    `refresh the context for {account_name}`. Available even when a
    Context Doc already exists, since re-running keeps it current.

### Triage panel

A modal opened by any stat tile. Shows only the matching accounts, each as
a compact row: name, health badge, and its Next Step line (plus a short
type-specific note — e.g. the disputed-ARR note when opened from the ARR
tile, or "swept Nd ago" when opened from the Stale Data tile). Clicking a
row closes the panel and scrolls to/briefly highlights that account's full
card on the page behind it. Escape or clicking the backdrop closes it.

### No-research-yet state

An account in `account-config.json` with no matching Context Doc found at
all (not "found but unparseable" — genuinely not found) renders as its own
card in the **No Health Data** group, with every field reading "No
research yet" and a "Refresh research" link that runs `account-context`
for the first time.

## What's left to the builder

- Exact regex/heuristics for each parsed field, beyond the matching rules
  stated above — the builder should look at a handful of real Context
  Docs (Goldman Sachs, Blink Health, ICON Clinical Research, Optum,
  Bristol Myers Squibb, found via Glean search during design) to calibrate
  patterns, and lean toward "Not captured this sweep" over a wrong guess
  whenever a pattern doesn't clearly match.
- The Flask route, template file naming, and exact Drive-search query
  construction (title search + `supportsAllDrives`), following the
  conventions already established in `gdrive_briefs.py` and
  `day_plan.html`'s route in `app.py`.
- Toolbar entry point: add a link to Portfolio in `brief_fragment.html`'s
  toolbar, matching the Day Plan link added previously (see
  `test_toolbar_day_plan_link.py` for the existing pattern to mirror).
- ARR-subtotal formatting for group headers and the Combined ARR stat tile
  (e.g. rounding/abbreviation rules) — no specific format was mandated
  here beyond matching the mockup's style (e.g. "$256K", "~$3.47M").
- Caching/performance: whether Context Doc lookups are cached per-request,
  per-session, or not at all for this first version. No daily cache
  contract was specified for Portfolio the way `daily-brief-generation`
  caches Customer Updates — Portfolio can do a live Drive read per page
  load for now; only optimize if page-load latency becomes a real problem.
- Mockups referenced above are UI/interaction ground truth; they were
  built and approved interactively during design at
  `.superpowers/brainstorm/` in the `day-planning-webapp` worktree
  (`my_customers_v3.html` — the final approved version, despite the old
  filename) and are not committed; recreate the relevant HTML/CSS/JS
  structure from this document rather than hunting for that file.
